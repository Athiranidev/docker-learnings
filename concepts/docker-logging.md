# Docker Logging

Docker logging is the process of capturing and viewing output generated by applications running inside containers.

## Basic Logging Flow

Application inside container
        ↓
stdout / stderr
        ↓
Docker logging system
        ↓
docker logs

Docker primarily captures the application's standard output (stdout) and standard error (stderr).

Example:

docker run --name logging-demo alpine sh -c 'echo "Application started"; echo "Something went wrong" >&2'

View logs:

docker logs logging-demo

Follow logs in real time:

docker logs -f logging-demo

Show only the latest lines:

docker logs --tail 50 logging-demo

Show logs with timestamps:

docker logs -t logging-demo

## stdout and stderr

stdout = normal application output

stderr = error or diagnostic output

Example:

echo "Application started"
echo "Something went wrong" >&2

The `>&2` redirects the second message to stderr.

Docker captures both streams when using its logging system.

## Logging Driver

A Docker logging driver determines how and where container logs are stored or sent.

Check the default logging driver:

docker info | grep "Logging Driver"

Check the logging driver of a specific container:

docker inspect <container> --format '{{.HostConfig.LogConfig.Type}}'

Common logging drivers:

json-file
local
syslog
journald
fluentd
awslogs

json-file stores container logs locally in JSON format.

local is optimized for local Docker logging and supports log rotation and compression.

Remote logging drivers can send logs to external systems.

Examples:

awslogs → AWS CloudWatch
syslog → Syslog server
fluentd → Fluentd collector
journald → systemd journal

## Log Rotation

Logs can continuously grow and consume disk space.

Example:

docker run -d \
  --name logging-demo \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  alpine \
  sh -c 'while true; do echo "application log"; sleep 1; done'

max-size=10m
→ Maximum size of an individual log file is approximately 10 MB.

max-file=3
→ Keep up to 3 log files when rotating.

Inspect logging configuration:

docker inspect logging-demo --format '{{.HostConfig.LogConfig.Type}} {{json .HostConfig.LogConfig.Config}}'

Container-specific logging configuration is normally specified when the container is created. Changing these settings generally requires recreating the container.

## Centralized Logging

With many containers or multiple servers, managing logs individually becomes difficult.

Instead, logs can be collected and sent to a centralized logging system.

Container A ─┐
Container B ─┤
Container C ─┼──→ Central Logging System
Container D ─┘

Examples of centralized logging systems:

AWS CloudWatch
ELK / Elastic Stack
Loki + Grafana

A common production flow is:

Application
    ↓
stdout / stderr
    ↓
Docker logging / logging agent
    ↓
Central logging system
    ↓
Search / monitoring / troubleshooting

## Why Logging Matters

Logs help engineers:

- Troubleshoot application failures
- Identify errors
- Understand application behavior
- Investigate incidents
- Monitor application activity
- Debug containers without entering them

`docker logs` is mainly useful for individual container troubleshooting.

Centralized logging becomes important when managing multiple containers, applications, or servers.

Application output
→ stdout / stderr

## Core Mental Model

`docker logs` = view container stdout/stderr

`Logging driver` = controls how Docker handles container logs

`Log rotation` = prevents logs from growing indefinitely

`Centralized logging` = collects logs from multiple containers/servers into one system
